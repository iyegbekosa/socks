# School Management Platform — Build Roadmap

**Spec:** [School Management Platform — System Design.pdf](../School%20Management%20Platform%20—%20System%20Design.pdf) (v0.1, Oct 11, 2026)
**Status:** Draft roadmap, 11 Oct 2026

This roadmap sequences the build of the system design into phases. Each phase ships working, tested software and gets its own implementation plan in `docs/superpowers/plans/` when work on it starts. Section 1 records where this roadmap departs from the design document; everything not listed there follows the design as written.

---

## 1. Changes to the design

### 1.1 Cloudinary replaces S3-compatible object storage

Affects design §3.3 (File storage), §3.5, §5.5, §7.2, §7.4, §9.1, §9.5, §11.4.

| Concern | Decision |
|---|---|
| Integration | A small custom Django `Storage` class over the `cloudinary` Python SDK (`core/storage.py`), not `django-cloudinary-storage`, so we control tenant prefixes and delivery type. |
| Tenant isolation | Every `public_id` is prefixed `{env}/{schema_name}/...` (e.g. `prod/greenfield/report_cards/2026-1/GFS-2026-0042`). The storage class reads the schema from the active connection and refuses to save without one. Matches the "files prefixed with schema name" rule in §7.2. |
| Public vs private files | School logos and branding: `type="upload"` (public). Everything about a child — photos, report cards, receipts, submissions, imports — `type="private"`. |
| Short-lived download links | Private files are served through `cloudinary.utils.private_download_url(..., expires_at=now + 10 min)`, generated by a Django view that first checks the requester's permission. Raw Cloudinary URLs are never stored in pages. |
| PDFs | Report cards and receipts are uploaded as `resource_type="raw"`. **Account setting needed:** enable "Allow delivery of PDF and ZIP files" in Cloudinary security settings (blocked by default on new accounts). |
| Images on 3G | Student photos and uploaded work images are delivered with `f_auto,q_auto` and size limits, which helps the "pages under 500 KB" target (§2.3). |
| Per-school storage quota | Tracked in our own `StoredFile` table (bytes, owner, kind) per tenant; `PlanLimits` reads it. Cloudinary usage is not queried per folder. |
| Upload safety | Type and size checks in Django before upload; evaluate Cloudinary's malware-detection add-on for student submissions. |
| Environments | Separate Cloudinary product environments (or at minimum `dev/`, `staging/` prefixes) so test data never mixes with production. |
| Backups | Enable Cloudinary backup on a paid plan for user uploads (photos, submissions). Report cards and receipts are regenerable from database data (§3.5), so they need no backup. |
| Cost | Cloudinary bills in credits (storage + bandwidth + transforms); the design's ~500 GB/year growth is expensive there. Mitigation: regenerate report-card/receipt PDFs on demand and delete stored copies after a school-set period; cap upload sizes per plan. Revisit before 50 schools. |
| Data protection | Cloudinary hosts outside Nigeria. Add Cloudinary to open question **Q1** (cross-border transfer under NDPA) and list it as a sub-processor in the data processing agreement (**Q6**). |

### 1.2 No parent portal — families use the student portal

Affects design §1.3, UC-09/12/14/17, FR-15, §5.1, §5.2, §6.2, §7.1, Q5.

| Concern | Decision |
|---|---|
| Accounts | Every student gets one login. Parents/guardians do **not** get accounts; they use their child's student login (for younger children the parent holds the login). This settles **Q5**: all students have logins. |
| Login | Admission number + password (young students have no phone or email). Password reset sends an OTP to the **primary guardian's phone** on file. Login rate limits (§6.4) apply per admission number and IP. |
| Guardians | Become contact records, not users: `guardian(student_id, name, phone, email, relationship, is_primary)`. Used for SMS/email (results ready, receipts, balances, absences), payment receipts and consent. Drop `guardian_link.user_id` and `can_pay`. |
| Student portal scope | Own results and report cards, own invoices, balances, **pay fees online**, receipts, attendance summary, assignments and materials, announcements. The "R self (if allowed)" restriction on report cards (§7.1) becomes a per-school setting that defaults to on. |
| Keeping parents informed | Because a teenager could hide results from a parent, key events go directly to guardian contacts by SMS/email: results published, receipt issued, balance reminders, absences. Parents stay informed without logging in. |
| Siblings (FR-15) | Replaced by a `family` record linking siblings via their shared primary guardian. A student's fee page shows a "pay for siblings too" option listing each sibling's outstanding balance, so one checkout still covers several invoices. Delivered in Phase 4 as a *Should*; per-student checkout is the minimum. |
| Consent (NDPA §7.7) | Guardian consent is recorded by the school at admission (form + checkbox in the admission screen), not at first login, because the person logging in may be the child. |
| Gateway customer | Paystack/Flutterwave require an email: use the primary guardian's email, or a school-generated placeholder when none exists. Receipt goes to guardian phone/email. |
| API | Remove `GET /me/children`; add `GET /me` (student profile, current class, balances). `GET /invoices` and `POST /payments/initialize` are scoped to the logged-in student (+ siblings in their family). |
| Access matrix | Remove the Parent row. Student row: Students R self · Report cards R self · Fees R own, pay · Learning R, submit · Messages R. |
| Capacity | User accounts drop from ~260,000 to ~103,000 (100,000 students + ~15 staff × 200 schools). |

## 2. Phases

Order is driven by dependencies: everything sits on tenancy; results and fees both need academics and students; the MVP must let a pilot school run a full term (scores in → report cards out → fees collected).

```
P0 Foundations ─► P1 Tenancy & accounts ─► P2 Academics & students ─┬─► P3 Results & report cards ─┐
                                                                     └─► P4 Fees & payments ─────────┤
                                                       P5 Communication (after P1; used by P3/P4) ───┤
                                                                                                     ▼
                                                                                         ★ MVP — pilot 3–5 schools
                                                                                                     │
                     P6 Attendance · P7 Learning · P8 Lifecycle & billing · P9 Launch hardening ◄────┘
                                                                                                     ▼
                                                                                         ★ Version 1 — general launch
```

### P0 — Foundations

**Goal:** an empty but deployable multi-tenant Django project with the safety nets in place before any feature.

- Git repo, Docker Compose dev stack (Django, Postgres 16, Redis, Celery worker + Beat, Mailpit), `*.localhost` tenant routing.
- Django LTS + DRF + `django-tenants`; `SHARED_APPS` / `TENANT_APPS` split; `School` and `Domain` models.
- `core/storage.py` Cloudinary storage with tenant prefixing and signed private downloads (§1.1).
- Celery tasks that require a schema name and run in `schema_context()` (task without one fails).
- Schema-prefixed Redis cache keys.
- Tenant-isolation test harness (two `TenantTestCase` schools; reusable "call as school A against school B's IDs" helper) — every later phase adds its endpoints to it.
- GitHub Actions: ruff, type checks, pytest, migration check, isolation suite.
- Structured JSON logging with request ID + schema; Sentry.
- Error format and status codes from §6.5; money helpers (integer kobo ↔ `₦` display).

**Exit:** two demo schools on `greenfield.localhost` / `bluewater.localhost`; a file uploaded in one cannot be downloaded from the other; CI green.

### P1 — Tenancy, onboarding and accounts

**Goal:** a school can sign up and its staff and students can log in.

- School signup → schema created, migrations run, defaults seeded (roles, levels, grading scale), first admin invited (UC-01, FR-01). Unknown hostnames show the platform landing page.
- Branding: logo (Cloudinary public), colours, motto, address on login page (FR-02).
- Accounts: staff (phone/email login, invite links, Argon2, lockout after 5 failures, 30-min staff session timeout, MFA for admin/principal/bursar) and **students (admission-number login, OTP reset to guardian phone)** (§1.2).
- Roles and permission framework matching the revised access matrix.
- Audit app: append-only `AuditEvent` for logins, failed logins, role changes.
- `PlanLimits` service (students, storage from `StoredFile`, SMS credits) — limits only; billing comes in P8.

**Exit:** self-service signup creates a usable school in under 2 minutes; isolation suite covers auth endpoints.

### P2 — Academics and students

**Goal:** the school's structure and student records exist.

- Session → Term (one current) → ClassLevel → ClassArm → Subject → SubjectOffering; streams; compulsory/elective (UC-03, UC-05, FR-03).
- Student admission with school-pattern admission numbers via locked counter row (FR-05); guardians as contacts; family/sibling linking; consent capture at admission (§1.2).
- Enrolment per session (history never overwritten).
- Bulk import of students and staff from Excel/CSV as a Celery job with row-level error report; 500 rows < 1 min (UC-04, FR-04). Imported files stored privately on Cloudinary.
- Student photos (private, `f_auto,q_auto`).

**Exit:** a pilot school's real class lists import cleanly; each student can log in and see their profile.

### P3 — Results and report cards

**Goal:** teachers enter scores and the school publishes correct, branded report cards. *Highest-risk module for school trust.*

- Assessment components per level, grading scale per school.
- Score grid (Excel-like, HTMX) + CSV upload; only assigned teachers (FR-06 → 403); optimistic `version` locking → 409 on clash.
- Computation: totals, grades, subject and class positions (with ties), term and cumulative averages (FR-07) in a Celery task; cached in `ResultSummary`, swapped in one transaction.
- Workflow Draft → Submitted → Reviewed → Approved → Published (locked); admin unlock audited (FR-08).
- Comments, affective/psychomotor ratings; broadsheet.
- WeasyPrint report-card PDFs in the `reports` queue → Cloudinary `raw` private; 50 cards < 2 min (FR-09). Student downloads via signed link.
- "Results published" SMS/email to guardians (uses P5).
- Results-accuracy check against a pilot school's hand-calculated broadsheet — exact match required.

**Exit:** one real past class reproduces the school's broadsheet exactly; students download report cards.

### P4 — Fees and payments

**Goal:** every naira paid is recorded once against the right student. *Highest-risk module for money.*

- Fee items, fee structure per level per term; invoices per student per term with discounts and balance brought forward (FR-10, FR-13).
- `PaymentGateway` adapter; Paystack first (pending **Q2**), with school subaccounts and split settlement (FR-11).
- Online payment flow from the student portal (§4.5 steps 1–7): `PaymentAttempt`, webhook signature + server verify + amount/currency match (FR-12), single atomic transaction with `select_for_update`, unique gateway reference, nightly/15-min re-verification.
- Sibling checkout through the family record (FR-15, revised).
- Manual payments with teller number/photo (Cloudinary private) and two-person approval above a school-set amount (UC-13).
- Sequential receipts (locked counter) as PDF; sent to guardian phone/email (FR-14).
- Debtors list (UC-14); optional result blocking for unpaid fees (UC-17).
- Integration tests for duplicate, delayed, out-of-order and failed webhooks in gateway test mode.

**Exit:** ₦100 test payment settles to a pilot school's account; duplicate webhooks cannot double-credit.

### P5 — Communication

Can start any time after P1; P3 and P4 call it.

- `notify(audience, channels, template, context)` service; queued, batched, delivery-logged (FR-16: 1,000 SMS queued < 10 s).
- SMS provider adapter (Termii or Africa's Talking) with fallback; email (SES/Postmark); in-app notifications.
- Templates with placeholders, quiet hours 9 pm–7 am, SMS credits per plan.
- Announcements to school/level/arm/debtors/individual (UC-15); fee reminders (UC-14).
- Audiences resolve to **guardian contacts** for family messages and to student accounts for in-app (§1.2).

**Exit:** a results-published notice reaches every guardian in a test class; delivery status visible.

### ★ MVP milestone — pilot with 3–5 schools

P0–P5 done. Run the review checklist items that apply (results accuracy, payment webhook tests, isolation suite, backup restore to staging). Start pilots at a **term start**, since schools set up fees and classes then. The next one is 2nd term, January 2027.

### P6 — Attendance

Daily register per arm in under a minute for 40 students on a phone (UC-06); optional absence SMS to guardians; term totals on the report card.

### P7 — Learning (Canvas-style)

Class pages per subject offering, modules, materials (Cloudinary; video by link only), assignments, submissions (private, size-capped per plan), grading, optional push of assignment scores into a CA component (UC-10).

### P8 — School lifecycle and platform billing

- Promotion wizard and graduation/alumni (UC-16, FR-17). **Must ship before the pilot schools' first session ends (July 2027).**
- Custom domains via Cloudflare custom hostnames with 10-minute DNS checks (UC-02).
- Subscription plans, per-term billing, 14-day grace then read-only, with fee payment still allowed (UC-18, FR-18) (pending **Q3**).
- Proprietor dashboard: enrolment, attendance, fee collection (UC-19).

### P9 — Launch hardening

- Offline score entry: IndexedDB drafts, sync with version check, "not yet saved" indicator.
- PWA install; 360 px viewport pass on every core flow; throttled-3G and low-end Android testing.
- Load test: 5,000 concurrent students viewing results, 500 payments in 10 minutes, p95 < 400 ms.
- Security: dependency scan, OWASP ZAP, external penetration test, CSP.
- NDPA: DPA with schools (Cloudinary listed as sub-processor), consent wording reviewed by counsel, DPO, data export/delete tools.
- Backups: Postgres PITR + cross-region copy; Cloudinary backup on; monthly restore test to staging; runbooks (§11.5).
- Monitoring and alerts from §11.2.

### ★ Version 1 — general launch

All review-checklist items in the design document are ticked, and open questions Q1–Q6 are answered and recorded.

### Later (unchanged from design §12.3)

- **Version 2:** Android app on the existing API, WhatsApp notifications, CBT exams, timetable, lesson-notes approval.
- **Version 3:** payroll and staff attendance, transport and hostel, cross-term analytics, teacher–family messaging (through the student portal).
